## 🔴 P0 — CRITICAL (ความปลอดภัย/integrity — ทำทันที)

### P0-1 · Provably-Fair พังสนิท — `serverSeed` ถูกส่งให้ client ตั้งแต่ขั้นที่ 1 ก่อนสับไพ่
- **ไฟล์:** `src/lib/security/session-token.ts:24-48` (payload มี `serverSeed: record.serverSeed`) + `src/app/api/reading/start/route.ts:86-98` (คืน `sessionToken` ตอน `serverSeed` ถูกเซ็ตแล้วแต่ `drawn` ยังไม่มี)
- **อาการ:** token = `base64url(JSON).HMAC` — **ไม่เข้ารหัส** ถอดด้วย `atob` ได้ทันที ข้างในมี `serverSeed` ครบ ผู้ใช้ decode token ตัวเองแล้วรู้ `serverSeed` ก่อนเลือก `clientSeed` → `drawCards()` เป็น deterministic จาก `sha256(serverSeed|clientSeed)` → คำนวณล่วงหน้าได้ว่า `clientSeed` ไหนให้ไพ่แบบที่ต้องการ → "shop" หาผลที่ชอบ การันตี "ปลอมไพ่ไม่ได้" ที่โฆษณาไว้ **เป็นเท็จ** แม้ตั้ง `TAROT_SESSION_SECRET` แล้วก็ตาม
- **วิธีแก้ (เลือกทางใดทางหนึ่ง, effort M):**
  - **แนะนำ:** เก็บ `serverSeed` ไว้ฝั่ง server เท่านั้น (Cloudflare KV keyed by reading id) ไม่ serialize ลง token เลย token เหลือแค่ `{id, exp}` + HMAC
  - หรือ: แยก token 2 ระยะ — pre-reveal token ถือแค่ `{id, spreadId, personaId, category, question, intake, nickname, safetyFlag, commitment}` (ไม่มี `serverSeed`) → เปิดเผย `serverSeed` เฉพาะใน response ของ `/read` ตอนจบ
  - ถ้าจำเป็นต้องเก็บ state ใน token จริง ๆ → **เข้ารหัส** ด้วย AES-GCM ไม่ใช่แค่ sign

### P0-2 · HMAC secret fallback เป็นค่าสาธารณะ — ปลอม token ได้ (regression ของ ISSUE-010b)
- **ไฟล์:** `src/lib/security/session-token.ts:16-22`
- **อาการ:** `TAROT_SESSION_SECRET || CF_PAGES_COMMIT_SHA || "tarot-sacred-altar-secret-provably-fair-2026"` — ค่า default เป็น string ใน repo **public**, `CF_PAGES_COMMIT_SHA` ก็ไม่ลับ (public repo) และ fail แบบ **เงียบ** `docs/KNOWN_ISSUES.md` เขียนว่า ISSUE-010b "แก้แล้ว (Hard fail loud)" — **ไม่จริง** โค้ดทำตรงข้าม ถ้า secret หลุด/ไม่ถูกเซ็ต attacker ปลอม token ที่มี `drawn[]` อะไรก็ได้, ตั้ง `safetyFlag:"none"` ถอด safety guard, ข้าม `checkQuestion`
- **วิธีแก้ (effort S):**
  1. ลบ `DEFAULT_DEV_SECRET` และ fallback `CF_PAGES_COMMIT_SHA` ออก
  2. `getSessionSecret()` → `throw` เมื่อ `process.env.NODE_ENV === "production"` และไม่มี `TAROT_SESSION_SECRET` (dev อนุญาต `TAROT_SESSION_SECRET_DEV` ที่ระบุชัด)
  3. บังคับความยาวขั้นต่ำ ≥ 32 bytes hex และ reject ค่า default เดิมแบบ explicit
  4. catch ที่ route boundary → คืน JSON 500 พร้อม body (นี่คือสาเหตุจริงของ INC-0025 — แก้ด้วย caught error ไม่ใช่ silent fallback)
  5. เพิ่ม log ตอน boot: `session-secret source=env|MISSING`
- **แก้แล้วต้องอัปเดต** `docs/KNOWN_ISSUES.md` ISSUE-010b ให้ตรงความจริง

### P0-3 · Token ไม่มีวันหมดอายุ + replay ได้ — `/start` token เอาไป re-roll การสับไพ่
- **ไฟล์:** `src/lib/security/session-token.ts:50-74` (ไม่มี `exp`/`iat`/nonce) · `src/app/api/reading/[id]/shuffle/route.ts:30-84` · `read/route.ts` · `chat/route.ts`
- **อาการ:** `verifyReadingSessionToken` เช็คแค่ HMAC + `id` ตรง `/shuffle` recovery path สร้าง record จาก `/start` token (ไม่มี `drawn`/`clientSeed`) แล้ว recompute `drawCards()` ด้วย `clientSeed` ที่ request ส่งมา บน Cloudflare isolate ที่เย็น (ไม่มี memory) → attacker เก็บ `/start` token เดิม, loop เรียก `/shuffle` ด้วย `clientSeed` ต่าง ๆ จนได้ไพ่ที่ชอบ แล้วค่อย `/read` — คอมเมนต์ "กันคนกดรีเฟรชสุ่มใหม่" **ไม่จริง** token ที่หลุด (history/ลิงก์แชร์/log) ใช้ได้ตลอดกาล
- **วิธีแก้ (effort M):**
  1. เพิ่ม `iat` + `exp` (2 ชม. ตรง store TTL) ใน payload และ enforce ใน `verifyReadingSessionToken`; รักษา `createdAt` เดิมตอน re-save
  2. `/shuffle` ต้อง **ปฏิเสธ** การ (re)compute draw ถ้า `record.drawn` มีอยู่แล้ว **หรือ** `record.clientSeed` ถูกล็อกแล้ว → คืนของเดิมเท่านั้น
  3. persist `serverSeed`/`clientSeed`/`drawn` ใน KV keyed by id → "ล็อกครั้งเดียว" เป็น global ไม่ใช่ per-isolate
  4. (เสริม) single-use nonce สำหรับ shuffle step บันทึกใน KV
