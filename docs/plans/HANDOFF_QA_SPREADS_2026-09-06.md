## 🔴 จุดเสี่ยงที่ต้องเพ่งเป็นพิเศษ: `monthly-ten`

พิกัดของ `monthly-ten` **ลอกมาจาก `celtic-cross` แต่เลื่อนไปทางขวา** — และ celtic-cross
**เคยล้นกรอบจนเป็น INC-0058 มาแล้ว**

| ผัง | ไพ่ใบที่ 6 (x) | คอลัมน์ขวา (x) | **ระยะห่าง** |
| :--- | :-: | :-: | :-: |
| `celtic-cross` (ของเดิม ผ่านการแก้มาแล้ว) | 0.50 | 0.72 | **0.22** |
| `monthly-ten` (ของใหม่) | 0.55 | 0.72 | **0.17** ⚠️ |

**ช่องว่างแคบกว่าเดิม 23%** → ความเสี่ยงไพ่ใบที่ 6 ซ้อนทับคอลัมน์ขวาบนจอแคบสูงกว่า celtic-cross
**ต้องวัดจริง อย่าเชื่อว่าลอกมาแล้วจะปลอดภัย**

พิกัดเต็มของ `monthly-ten` (ไว้เทียบตอนตรวจ):

```
#1  x=0.35 y=0.5              #6  x=0.55 y=0.5
#2  x=0.35 y=0.5  rotate:90   #7  x=0.72 y=0.8
#3  x=0.35 y=0.8              #8  x=0.72 y=0.6
#4  x=0.15 y=0.5              #9  x=0.72 y=0.4
#5  x=0.35 y=0.2              #10 x=0.72 y=0.2
```

> ✅ **ยืนยันแล้วว่าไม่ใช่บั๊ก**: ใบ #1 กับ #2 มีพิกัดเดียวกันโดยตั้งใจ เพราะ #2 มี `rotate: 90`
> วางขวางทับใบแรกแบบเดียวกับ celtic-cross — **อย่าไป "แก้" ให้มันแยกกัน**

### ต้องตรวจเพิ่มสำหรับใบที่หมุน (บทเรียน INC-0070)

ใบ #2 ของ `monthly-ten` หมุน 90° → **เลข "2" ต้องตั้งตรง ไม่หมุนตามการ์ด**
กฎถาวรจาก INC-0070: *"ป้ายกำกับในไดอะแกรมที่กล่องแม่ถูกหมุน ต้องห่อด้วย span ที่ counter-rotate"*

ตรวจที่ `/spreads/monthly-ten` — ถ้าเลข 2 อ่านเป็น "N" หรือเอียง แปลว่า counter-rotate ไม่ทำงานกับผังใหม่

# 🅱️ งาน B · 🔴 ปิดช่องโหว่ `guestAllowed` ที่ประกาศไว้แต่ไม่มีผลบังคับ

## สิ่งที่พบระหว่างเตรียมแผนนี้ (ของจริง ไม่ใช่ข้อสงสัย)

`Spread` มีฟิลด์ `guestAllowed` ที่อ่านแล้วเข้าใจว่า "ผังนี้ให้ผู้เยี่ยมชมใช้ได้หรือไม่"
**แต่ไม่มีโค้ดฝั่งรันไทม์อ่านมันเลยแม้แต่บรรทัดเดียว**

```bash
grep -rn "guestAllowed" src/ scripts/ | grep -v "data/spreads.ts"
# ผลลัพธ์: เจอแค่ใน scripts/qa/test-quick-fortune.ts และ scripts/qa/test-seo-wave3.ts
# ไม่มีใน src/ เลย → ไม่มีผลต่อพฤติกรรมจริง
```

ตัวที่บังคับจริงคือ `STANDARD_SPREAD_IDS` ใน [`src/lib/entitlement/limits.ts`](../../src/lib/entitlement/limits.ts)
ซึ่งถูกอ่านที่ [`src/app/api/reading/start/route.ts:122`](../../src/app/api/reading/start/route.ts) และ
[`src/app/TarotFlow.tsx:478`](../../src/app/TarotFlow.tsx)

## ผลที่ตามมา — 5 ผังปัจจุบันขัดกันเองอยู่

```
ผัง                  guestAllowed    อยู่ใน STANDARD_SPREAD_IDS    guest เปิดได้จริงไหม
yes-no               false           ✅ ใช่                        ✅ เปิดได้
three-card           false           ✅ ใช่                        ✅ เปิดได้
situation-solution   false           ✅ ใช่                        ✅ เปิดได้
mind-body-spirit     false           ✅ ใช่                        ✅ เปิดได้
how-they-feel        false           ✅ ใช่                        ✅ เปิดได้
```

**ทั้ง 5 ผังนี้เขียนไว้ว่าไม่ให้ guest ใช้ แต่ความจริง guest ใช้ได้หมด**

### ทำไมเรื่องนี้อันตราย

1. **คนอ่านโค้ดถูกหลอก** — ใครก็ตามที่ตั้ง `guestAllowed: false` ให้ผังใหม่จะเชื่อว่าล็อกแล้ว
   ทั้งที่ไม่ได้ล็อกอะไรเลย นี่คือรูปแบบเดียวกับ **ISSUE-021** (`EntitlementGate` รับ props มาแล้วไม่ใช้)
2. **ด่านตรวจกำลังยืนยันสิ่งที่ไม่มีผล** — [`test-seo-wave3.ts:43,51`](../../scripts/qa/test-seo-wave3.ts)
   ตรวจว่า `guestAllowed === true/false` ซึ่งเป็นการตรวจฟิลด์ที่ไม่ได้ควบคุมอะไร
   **ด่านเขียวแต่ไม่ได้พิสูจน์พฤติกรรมจริง** — ตรงกับบทเรียน INC-0044 เรื่องด่านที่ให้ความมั่นใจผิด ๆ

## ✅ ทางแก้ — เลือก 1 ใน 2 แล้วทำให้สุด

### ทางเลือกที่ 1 (แนะนำ) · ทำให้ `guestAllowed` เป็นแหล่งความจริงจริง ๆ

- ให้ `isStandardSpread()` (หรือกฎฝั่ง guest) อ่านจาก `SPREADS` ผ่าน `guestAllowed` แทนการมีลิสต์ซ้ำสองที่
- แก้ `guestAllowed` ของ 5 ผังข้างบนให้เป็น `true` ให้ตรงกับพฤติกรรมจริงที่ใช้มาตลอด
  (**ห้ามเปลี่ยนพฤติกรรม** — เปลี่ยนแค่ให้ฟิลด์ตรงกับความจริง ไม่งั้นผู้ใช้เดิมจะเสียสิทธิ์ที่เคยมีอยู่)
- **ข้อดี**: ปิดปัญหา "ลิสต์ซ้ำสองที่" ถาวร ตรงกับบทเรียน INC-0005 (*"ห้ามเขียนรายการซ้ำมากกว่าหนึ่งที่เด็ดขาด"*)

### ทางเลือกที่ 2 · ลบ `guestAllowed` ทิ้ง

# 🅳 งาน D · ลด false positive ของด่าน `test-docs-numbers.ts`

## สิ่งที่เกิดขึ้นจริงตอนเขียนเอกสารฉบับนี้

ตอน commit เอกสารนี้ ด่าน `test-docs-numbers.ts` **บล็อกทันที 5 จุด** ด้วยข้อความ:

```
docs/KNOWN_ISSUES.md:31 [จำนวนผัง (N ผัง)] → พบ "5 ผัง" (5) แต่ของจริงคือ 25
   เนื้อหา: ### ISSUE-032 · ผังใหม่ 5 ผังยังไม่เคยถูกใช้งานจริงสักครั้ง
```

แต่ **"ผังใหม่ 5 ผัง" ไม่ได้อ้างยอดรวม** — มันบอกจำนวนผังที่เพิ่มใหม่ในคลื่น 3 ซึ่งเป็นเลขที่ถูกต้อง
กฎ `(?<!ไพ่\s)(\d+)\s*ผัง` แยกไม่ออกระหว่าง **"ยอดรวมทั้งระบบ"** กับ **"จำนวนของชุดย่อย"**

> ผู้เขียนด่านคิดเผื่อไว้แล้วบางส่วน (มี `(?<!ไพ่\s)` กันคำว่า "ไพ่ 5 ใบ") — แค่ยังไม่ครอบคลุมคำขยายอื่น

## ทำไมต้องแก้ ไม่ใช่แค่ใส่ ALLOWLIST ไปเรื่อย ๆ

บทเรียน **INC-0044** เขียนไว้ตรง ๆ:

> *"การรายงานผิดอันตรายกว่าไม่รายงาน — มันไปกล่าวหาคนที่ทำถูกแล้ว และทำให้คนเลิกเชื่อคำเตือนนั้นทั้งหมด"*

ถ้าปล่อยไว้ ทุกคนที่เขียนเอกสารด้วยภาษาไทยธรรมชาติจะโดนบล็อกเรื่อย ๆ แล้วสุดท้ายจะเริ่ม
ใส่ `ALLOWLIST` แบบไม่คิด ซึ่งทำให้ด่านหมดความหมายไปเลย

## ทางแก้ที่เสนอ

เพิ่ม negative lookbehind สำหรับคำขยายที่บ่งบอกว่าเป็น **ชุดย่อย ไม่ใช่ยอดรวม**:

```ts
// ── before ─────────────────────────────────────────────
{ name: "จำนวนผัง (N ผัง)", re: /(?<!ไพ่\s)(\d+)\s*ผัง/g, expected: TRUTH.spreads },

// ── after ──────────────────────────────────────────────
// กันคำขยายที่บ่งบอกว่าเป็นชุดย่อย ไม่ใช่ยอดรวมทั้งระบบ
// (เช่น "ผังใหม่ 5 ผัง" · "ผังฟรี 3 ผัง" · "ไพ่ 5 ใบ")
{
  name: "จำนวนผัง (N ผัง)",
  re: /(?<!ไพ่\s)(?<!ใหม่\s)(?<!ฟรี\s)(?<!ล็อก\s)(?<!เพิ่ม\s)(?<!ทั้ง\s)(\d+)\s*ผัง/g,
  expected: TRUTH.spreads,
},
```

> 💡 **ตัวเลือกที่แข็งแรงกว่า** (ถ้ามีเวลา): เปลี่ยนจาก "จับทุกที่แล้วยกเว้นทีละคำ" เป็น
> **"จับเฉพาะรูปประโยคที่อ้างยอดรวมจริง ๆ"** เช่นบังคับว่าต้องมีคำว่า `คลัง` `ทั้งหมด` `ครบ` `รองรับ`
> อยู่ใกล้ ๆ — วิธีนี้ปลอดภัยกว่าเพราะ default คือ "ไม่จับ" ไม่ใช่ "จับไว้ก่อน"
