### W1.2 · ต่อ Karmic Bridge เข้ากับประวัติจริง 🔥

#### `src/lib/ai/memory.ts` (ไฟล์ใหม่)

```ts
import { listJournal } from "@/lib/journal/journal.repo";
import type { PastReadingSnapshot } from "@/lib/ai/karmic";

/**
 * 🧠 ความทรงจำข้ามครั้งของแม่หมอ
 * ส่ง **เฉพาะรูปย่อ** ไม่ส่งคำอ่านเต็ม เพราะ:
 *  1. prompt ยาวขึ้น = ช้าลงและแพงขึ้นทุกครั้ง
 *  2. ข้อมูลอ่อนไหวควรออกจากระบบเราน้อยที่สุด (PDPA)
 *  3. สิ่งที่โมเดลต้องรู้จริง ๆ คือ "เคยได้ไพ่อะไร ถามอะไร แล้วจริงไหม"
 * ⚠️ ผู้เยี่ยมชมไม่มีประวัติ → คืน undefined เงียบ ๆ ห้าม throw
 */
export async function loadKarmicMemory(
  userId: string | null | undefined,
  limit = 3,
): Promise<PastReadingSnapshot | undefined> {
  if (!userId) return undefined;
  try {
    const past = await listJournal(userId, { limit });
    const latest = past[0];
    if (!latest?.cards?.length) return undefined;
    return {
      primaryCardName: latest.cards[0].cardNameTh,
      question: latest.question,
      outcome: latest.outcome,
      daysAgo: Math.floor((Date.now() - new Date(latest.date).getTime()) / 86_400_000),
      recentPrimaryCards: past.slice(1).map((r) => r.cards[0]?.cardNameTh).filter(Boolean),
    };
  } catch (err) {
    console.warn("[karmic memory] อ่านประวัติไม่สำเร็จ:", err);
    return undefined;   // ประวัติอ่านไม่ได้ = คำอ่านต้องทำงานต่อได้
  }
}
```

- `prompt.ts` — เพิ่ม `pastReading?` ใน `ReadingContext` แล้วเปลี่ยนบรรทัด 167 เป็น `analyzeKarmicBridge(cards, ctx.pastReading)`
- `read/route.ts` — `readingCtx` มี `viewer` อยู่แล้วจากบรรทัด 108

> ⚠️ **ความเร็ว**: การอ่าน D1 นี้อยู่**ก่อน**สตรีมเริ่ม → กระทบ TTFB โดยตรง
> ต้องยิงขนานด้วย `Promise.all` กับ `getContentOverrides()` **ไม่ใช่ต่อคิว**
> ถ้าเกินงบ 300ms ให้ตั้ง timeout 200ms แล้วปล่อยผ่าน

## 3. 🌊 คลื่นที่ 2 — ยกคุณภาพคำอ่าน

### W2.1 · ถามกลับก่อนสับไพ่ 🥇 คันโยกที่ใหญ่ที่สุด

**ปัญหา**: `IntentionAltarInput` เป็นฟอร์มนิ่ง — ช่องสถานการณ์ + ชิปสำเร็จรูป + ช่องคำถาม แล้วไปสับไพ่เลย

แม่หมอตัวจริง**ถามกลับก่อน**:
> ผู้ใช้: "เขาจะกลับมาไหม"
> แม่หมอ: "ขอถามหน่อยนะคะ — เลิกกันนานแค่ไหนแล้ว แล้วตอนนี้ยังคุยกันอยู่หรือเปล่า"

คำถามแรกตอบให้ดีไม่ได้ไม่ว่าโมเดลจะเก่งแค่ไหน เพราะข้อมูลไม่พอ
แต่พอรู้ว่า *"เลิกกัน 3 เดือน ยังคุยกันอยู่ เขาเพิ่งมีคนใหม่"* คำอ่านคมขึ้นคนละโลก

**วิธีทำ**: หลังผู้ใช้กรอกคำถามเสร็จ เรียกโมเดลเล็ก 1 ครั้ง ตัดสินว่า

```ts
{ needsClarification: boolean; question?: string; reason?: string }
```

ถ้าต้องถาม → แสดง 1 คำถาม (ข้ามได้) แล้วเก็บคำตอบเข้า `intake` ที่มีอยู่แล้ว

**ข้อดีพิเศษ**:
- **ไม่กระทบ TTFB ของคำอ่านเลย** เพราะเกิดก่อนพิธีสับไพ่
- **เข้ากับพิธีกรรมพอดี** — ทำให้เหมือนแม่หมอจริงมากขึ้นด้วยซ้ำ ไม่ใช่ขั้นตอนแปลกปลอม

**ข้อควรระวัง**
- ต้อง **ข้ามได้เสมอ** — ผู้ใช้ที่รีบต้องกดผ่านได้ ห้ามบังคับ
- ถามแค่ **1 ข้อ** ห้ามซัก 3 ข้อจนน่ารำคาญ
- ต้องผ่าน `isAiCapReached()` และนับด้วย `recordAiCall()`
- คำถามที่ชัดอยู่แล้วต้องไม่ถาม (ไม่งั้นกวนใจคนที่เตรียมคำถามมาดี)

**✅ เกณฑ์ผ่าน**
- [ ] คำถามกำกวม ("เขาจะกลับมาไหม") → ถามกลับ
- [ ] คำถามที่ชัดแล้ว → **ไม่ถาม** ไปสับไพ่เลย
- [ ] กดข้าม → ไปต่อได้ทันที
- [ ] เพดาน AI เต็ม / โมเดลล้ม → ข้ามขั้นนี้เงียบ ๆ ไม่บล็อกผู้ใช้
- [ ] `judge_score` ของคำอ่านที่ผ่านการถามกลับ **สูงกว่า** ที่ไม่ผ่านอย่างมีนัย

**ขนาดงาน** ~1-1.5 วัน (มี UI ด้วย) · **ต้นทุน AI** +1 call เล็ก ต่อการเปิดไพ่ 1 รอบ

### W2.2 · บังคับให้เหตุผลปรากฏในโครงสร้าง

**ปัญหา**: ตอนนี้โมเดลได้ความหมายไพ่เป็นข้อความแล้วเชื่อมโยงอิสระ — ตรวจไม่ได้ว่ามันอ่านจากอะไร

**วิธีทำ**: ขยาย `CardReadingSchema` ให้บังคับระบุที่มาของคำอ่าน

```ts
export const CardReadingSchema = z.object({
  position: z.number().int().min(0),
  headline: z.string().min(1).max(80),
  // ── ใหม่: บังคับให้เหตุผลปรากฏ ────────────────────────────────
  visualAnchor: z.string().min(1)
    .describe("องค์ประกอบบนหน้าไพ่ 1909 ที่ใช้อ่านจริง เช่น 'ชายชูถ้วยขึ้นสูง' 'สุนัขเห่าที่เท้า'"),
  positionLink: z.string().min(1)
    .describe("ไพ่ใบนี้ตอบมิติของตำแหน่งนี้อย่างไร"),
  questionLink: z.string().min(1)
    .describe("เชื่อมกับส่วนไหนของคำถามผู้ถามโดยตรง"),
  reading: z.string().min(1),
});
```

**ทำไมได้ผล**: บังคับให้เหตุผลเป็น**โครงสร้าง** ไม่ใช่หวังว่าโมเดลจะคิดเอง
และทำให้ **W1.3 ตรวจได้ว่า `visualAnchor` มีอยู่จริงบนไพ่ใบนั้นไหม** (เทียบกับ `visual-lore.ts`)

> ⚠️ **UI ไม่ต้องแสดงฟิลด์ใหม่ทั้งหมด** — เก็บไว้ตรวจสอบและอาจโชว์เป็น "ที่มาของคำอ่าน" แบบพับเก็บได้
> ⚠️ เพิ่มฟิลด์ = เพิ่ม output tokens → ต้องเช็คว่า `max_tokens` ยังพอ (สูตรปัจจุบัน `1600 + 340×ใบ`)

**✅ เกณฑ์ผ่าน**
- [ ] ทุกใบมี `visualAnchor` ที่ตรวจแล้วว่ามีอยู่จริงใน `visual-lore.ts`
- [ ] `judge_score` เกณฑ์ "ยึดกับภาพไพ่จริง" **สูงขึ้น**
- [ ] คำอ่านไม่ถูกตัดกลางเพราะ token ไม่พอ (เฝ้า `had_failover`)

**ขนาดงาน** ~1 วัน

### W3.1 · คลังคำอ่านที่พิสูจน์แล้วว่าแม่น → ดึงมาเป็นตัวอย่าง 🥉

**ปัญหาปัจจุบัน**: `SYSTEM_CORE_KNOWLEDGE` (7,334 ตัวอักษร) มีตัวอย่างคำอ่านมาตรฐาน **แค่ 1 ชิ้น**
(เคส *ผัง 1 ใบ หมวดการงาน*) ใช้สอนทุกหมวดและทุกขนาดผัง — ผัง 10 ใบหมวดความรักถูกสอนด้วยตัวอย่างที่หน้าตาไม่เหมือนงานเลย

**ทำไมนี่คือของจริง**: ระบบ**เก่งขึ้นเองตามจำนวนผู้ใช้** เป็นสินทรัพย์ที่ทบต้นและคู่แข่งลอกไม่ได้ เพราะไม่มีข้อมูลนี้

**ระยะเริ่มต้น** (ยังไม่มีข้อมูลพอ): ใช้คลังที่คัดเอง 6-8 ชิ้นครอบคลุม (หมวด × ขนาดผัง) ไปก่อน แล้วค่อยสลับเป็นของจริงเมื่อข้อมูลถึงเกณฑ์

> ⚠️ **กับดัก prompt cache**: `buildSystemPrompt()` ถูกออกแบบให้คงที่ต่อ persona เพื่อ caching (คอมเมนต์ `prompt.ts:16-22`)

> ⚠️ ตัวอย่างต้องผ่าน W1.3 ก่อนเข้าคลัง — ไม่งั้นสอนพฤติกรรมผิดให้โมเดล

- [ ] ผังความรัก 3 ใบ → ได้ตัวอย่างหมวดความรัก 3 ใบ
- [ ] ไม่มีตัวอย่างตรง → fallback ได้ ไม่ throw
- [ ] system prompt ต่อครั้ง **ไม่ยาวขึ้น** กว่าเดิม
- [ ] อัตรา `ACCURATE` ของ `prompt_version` ใหม่ **ไม่ต่ำกว่า** เดิม หลังเก็บ ≥1 สัปดาห์

### W3.3 · RAG บทความจากคลัง Vectorize

```ts
/**
 * ⚠️ ดึง "บทความ" เท่านั้น ไม่ดึง "ไพ่"
 * ข้อมูลไพ่ที่เปิดถูกส่งเข้า prompt ครบแล้วผ่าน formatCardLoreForPrompt()
 * ถ้าดึงไพ่ใบอื่นเข้ามาด้วย = ยัดไพ่ที่ไม่ได้เปิดเข้าบริบท → เสี่ยงผิดกฎเหล็กข้อ 14 โดยตรง
 */
export async function retrieveReadingContext(question: string, category: Category): Promise<string> {
  const hits = await semanticSearch(`${question} ${category}`, { topK: 2, type: "article" });
  return hits.map((h) => `• ${h.title}: ${h.snippet}`).join("\n");
}
```

**ผลพลอยได้**: คำอ่านอ้างอิงบทความของเราเองได้ → ลิงก์ภายในและเวลาอยู่บนเว็บเพิ่ม

> ⚠️ **บังคับ**: ยิงขนานด้วย `Promise.all` · timeout **250ms** ไม่ทันปล่อยผ่าน · แคชผลใน KV ตามคู่ (หมวด × คำถามที่ normalize)

**✅ เกณฑ์ผ่าน**
- [ ] Vectorize ล่ม/timeout → คำอ่านออกปกติ
- [ ] **TTFB ไม่แย่ลงเกิน 300ms**
- [ ] อัตรา `FOREIGN_CARD` จาก W1.3 **ไม่เพิ่มขึ้น**

**ขนาดงาน** ~1-2 วัน

## 8. วัดยังไงว่าฉลาดขึ้นจริง + กติกาย้อนกลับ

| ชั้น | ตัวชี้วัด | อ่านจากไหน |
| :--- | :--- | :--- |
| **ผู้ใช้บอกเอง** (หลัก) | สัดส่วน `ACCURATE` · อัตรา `NOT_HAPPENED` ที่ต้องลดลง | `reading_quality.outcome` |
| **LLM judge** (รอง — วนรอบเร็ว) | `judge_score` 1-5 แยกตาม rubric 5 เกณฑ์ | `reading_quality.judge_score` |
| **พฤติกรรม** | สัดส่วนคนกดแชทถามต่อ · จำนวนคำถามต่อรอบ · อัตรากลับมาเปิดซ้ำ | `recordEvent` |
| **ระบบ** | failover · `ai_severe_foreign_leak` · `ai_consistency_fail` · TTFB | `/admin` |

### กติกาย้อนกลับ

**แก้ prompt ครั้งไหนต้องขึ้น `PROMPT_VERSION` แล้วเทียบก่อน/หลังอย่างน้อย 1 สัปดาห์**

| สัญญาณ | ทำอะไร |
| :--- | :--- |
| `ACCURATE` ลดลง | **ย้อนกลับ** ไม่ใช่แก้เพิ่มทับ |
| `NOT_HAPPENED` เพิ่มขึ้น | ย้อนกลับทันที (แย่กว่า `ACCURATE` ลด) |
| `elapsed_ms` เพิ่มเกิน 300ms | ย้อนกลับ หรือย้ายงานไปหลังสตรีม |
| `ai_consistency_fail` พุ่ง | ตรวจว่าด่านเข้มเกินไปหรือคุณภาพตกจริง **ก่อน**ปิดด่าน |
