# 🧠 แผนยกระดับความฉลาดของแม่หมอ AI (AI Reading Intelligence Plan)

> **สถานะ**: ข้อเสนอ รอเจ้าของโปรเจกต์เลือกเฟสที่จะทำ
> **วันที่สำรวจ**: 2026-09-04 · อ้างอิงโค้ดจริงบน `main` commit `7beb1cf`
> **หลักการ**: ทุกข้อในเอกสารนี้มาจากการอ่านโค้ดจริง ไม่ใช่คำแนะนำทั่วไปที่ใช้กับเว็บไหนก็ได้

## 0. สิ่งที่ระบบทำได้ดีอยู่แล้ว (อย่าเผลอรื้อ)

ก่อนเสนออะไรใหม่ ต้องบันทึกไว้ว่าของเดิมแข็งแรงตรงไหน:

| ของที่มี | ทำไมถึงดี |
| :--- | :--- |
| **7 โมดูลวิเคราะห์เชิงสัญลักษณ์** (`alchemy` `cosmic` `gaze` `numerology` `intent` `ritual` `karmic`) | คำนวณ**ก่อน**ส่งเข้าโมเดล = โมเดลไม่ต้องเดาเอง ลดการมั่วลงมหาศาล นี่คือเทคนิคที่ถูกต้องแล้ว (deterministic priors) |
| **`formatCardLoreForPrompt()`** ป้อนรายละเอียดภาพ 1909 จริงรายใบ | คำอ่านอ้างอิงภาพจริงได้ ไม่ใช่ความจำเลือน ๆ ของโมเดล |
| **คุมความยาวตามจำนวนไพ่** (`depth` ที่ `prompt.ts:196`) | ผัง 10 ใบไม่กลายเป็นกำแพงข้อความ · ผัง 1 ใบได้ความลึก |
| **ด่านภาษาต่างด้าว 2 ระดับ + failover Groq→Gemini** | ปัญหาคำอ่านหลุดภาษาจีนถูกจัดการเป็นระบบแล้ว |
| **`response_format: json_object` + `ReadingSchema`** | ผลลัพธ์มีโครงสร้างบังคับ ไม่ต้อง parse ข้อความอิสระ |

**สรุป: prompt engineering ระดับพื้นฐานถึงกลางทำครบแล้ว** สิ่งที่ขาดไม่ใช่ "เขียน prompt ให้ดีขึ้น" แต่เป็น **ข้อมูลรอบตัวคำอ่าน** และ **วงจรวัดผล**

## 1. 🔌 สามระบบที่ "สร้างไว้แล้วแต่ไม่ได้เสียบปลั๊ก"

นี่คือของที่ได้ผลเร็วที่สุด เพราะโค้ดมีอยู่แล้ว แค่ต่อสาย

### 1.1 🔴 Karmic Bridge — โมดูลที่ทำงานไม่ได้เลยแม้แต่ครั้งเดียว

`src/lib/ai/prompt.ts:167`

```ts
const karmic = analyzeKarmicBridge(cards);   // ← ส่งมาแค่ไพ่
```

แต่ลายเซ็นฟังก์ชันคือ `src/lib/ai/karmic.ts:44`

```ts
export function analyzeKarmicBridge(
  currentCards: TarotCard[],
  pastReading?: PastReadingSnapshot        // ← ไม่เคยมีใครส่งเข้ามา
): KarmicBridgeAnalysis {
  if (!pastReading || !pastReading.primaryCardName) {
    return { hasPastContext: false };      // ← ออกตรงนี้ 100% ของทุกครั้ง
  }
```

**ผลคือโมดูล 89 บรรทัดพร้อมตาราง `NOTABLE_TRANSITIONS` ไม่เคยผลิตข้อความออกมาสักครั้ง** และบรรทัด
`${karmic.karmicNarrative ? ... : ""}` ใน prompt เป็นสตริงว่างเสมอ

> ที่น่าเสียดายคือ **ข้อมูลมีอยู่ครบแล้ว** — ตาราง `reading_journal` ใน D1 เก็บประวัติทุกครั้ง
> และ `read/route.ts:108` ก็เรียก `getViewer(request)` อยู่แล้ว รู้ว่าใครกำลังเปิดไพ่

**นี่คือฟีเจอร์ที่แยกเว็บดูดวงธรรมดาออกจากเว็บที่ "แม่หมอจำเราได้"** — และมันปิดอยู่

### 1.2 🟠 คลังค้นหาเชิงความหมาย (Vectorize) ไม่ถูกใช้ตอนอ่านไพ่เลย

`src/lib/search/vectorize.ts` มี index ของ **ไพ่ 78 ใบ + บทความ 24 ชิ้น** (มีด่าน `repo:verify` เฝ้าอยู่ด้วย)

แต่ผู้เรียกมีแค่ 2 ที่:
- `src/app/api/search/route.ts` — ช่องค้นหาของผู้ใช้
- `src/app/api/admin/rebuild-search-index/route.ts` — ปุ่มสร้าง index ใหม่

**คำอ่านไพ่ไม่เคยดึงอะไรจากคลังนี้เลย** ทั้งที่มันคือฐาน RAG ที่สร้างเสร็จแล้ว

### 1.3 🟠 คะแนนความแม่นที่ผู้ใช้ให้ ไม่ถูกนำไปใช้ปรับปรุงอะไร

ผู้ใช้กดได้ว่า `ACCURATE` / `PARTIAL` / `NOT_HAPPENED` เก็บลง `reading_journal.outcome`

แต่ถูกอ่านกลับมาแค่ 2 ที่ และเป็นการ**แสดงผลให้เจ้าตัวดูเท่านั้น**:
- `journal/monthly-summary/route.ts:63` — สรุปรายเดือนของผู้ใช้คนนั้น
- `ReadingHistoryModal.tsx` — ตัวกรองในหน้าประวัติ

**ไม่มีที่ไหนรวมสถิติว่า persona ไหน / ผังไหน / โมเดลไหน แม่นกว่ากัน**

> ⚠️ **นี่คือข้อที่สำคัญที่สุดในเอกสารนี้** ถ้าไม่มีตัวเลขนี้ ทุกการปรับ prompt หลังจากนี้
> จะตัดสินได้แค่ "รู้สึกว่าดีขึ้น" ซึ่งเชื่อถือไม่ได้ และไม่มีทางรู้ว่าการแก้ครั้งไหนทำให้แย่ลง

## 2. 📐 เฟส 0 — สร้างเครื่องวัดก่อน (ต้องทำก่อนทุกอย่าง)

> **หลักการโปรเจกต์ข้อ 0.2.1 "วัดก่อนเดา"** — ถ้าไม่มีตัวเลข การปรับ AI จะกลายเป็นการเดาแบบมีต้นทุน

### 2.1 ตารางสถิติคุณภาพคำอ่าน

เพิ่มคอลัมน์ที่ `reading_journal` (หรือตารางใหม่ `reading_quality`) เก็บ **บริบทตอนสร้างคำอ่าน**:

| ฟิลด์ | ทำไมต้องเก็บ |
| :--- | :--- |
| `provider` (`groq` / `gemini`) | รู้ว่าโมเดลไหนแม่นกว่า |
| `model` | เทียบระหว่างโมเดลใน provider เดียวกัน |
| `persona_id` | `AccuracyRatingWidget` รับ `personaId` มาอยู่แล้วแต่ไม่ได้ใช้ |
| `spread_id` · `card_count` | ผังใหญ่แม่นน้อยกว่าผังเล็กไหม |
| `prompt_version` | **สำคัญที่สุด** — เทียบก่อน/หลังแก้ prompt ได้จริง |
| `elapsed_ms` · `output_tokens` | ดูว่าคุณภาพแลกมากับเวลา/ต้นทุนเท่าไร |

### 2.2 การ์ดใน `/admin`

แสดง `outcome` แยกตามมิติข้างบน + อัตรา `NOT_HAPPENED` ที่เป็นสัญญาณเตือน

### 2.3 ชุดข้อสอบถาวร (Golden Set)

เก็บเคสจริง 30-50 เคส (คำถาม + ไพ่ที่ออก) ที่หลากหลายหมวดและขนาดผัง ไว้รันซ้ำได้ทุกครั้งที่แก้ prompt
ต่อยอดจาก `scripts/qa/test-ai-reading-golden.ts` ที่มีโครงอยู่แล้ว

> ตอนนี้ไฟล์นั้นตรวจแค่ "โครงสร้าง prompt ถูกไหม" ยังไม่ได้ตรวจ **คุณภาพคำอ่านจริง**

**ต้นทุน**: ~1 วัน · **ผลตอบแทน**: ทุกเฟสหลังจากนี้พิสูจน์ผลได้

## 3. 🚀 เฟส 1 — เสียบปลั๊กของที่มีอยู่ (คุ้มที่สุด)

### 3.1 ต่อ Karmic Bridge เข้ากับประวัติจริง

**ทำอะไร**: ดึงคำอ่านล่าสุด 1-3 ครั้งของผู้ใช้จาก `reading_journal` ส่งเข้า `analyzeKarmicBridge()`

**เทคนิคที่ใช้**: *Longitudinal Context* — ให้โมเดลเห็นเส้นทางของผู้ใช้ ไม่ใช่แค่จุดเดียว

**ผลที่ผู้ใช้รู้สึก**:
> "ครั้งก่อนคุณเปิดได้ไพ่หอคอย ตอนนั้นทุกอย่างกำลังพังลง — วันนี้ไพ่ดาวมาแทน นี่คือช่วงเยียวยาหลังพายุ"

นี่คือประโยคที่เว็บดูดวงทั่วไปพูดไม่ได้ เพราะไม่มีความทรงจำ

**ข้อควรระวัง**:
- ผู้เยี่ยมชม (guest) ไม่มีประวัติ → ต้อง degrade เงียบ ๆ ไม่ใช่พัง
- **PDPA**: ใช้ประวัติของเจ้าตัวเองเพื่อตอบเจ้าตัวเอง = ทำได้ · แต่ต้องลบตามไปเมื่อผู้ใช้ขอลบบัญชี (`softDeleteUser` มีอยู่แล้ว ตรวจว่าครอบคลุม)
- ขยาย `NOTABLE_TRANSITIONS` ให้ครอบคลุมกว่าเดิม หรือให้โมเดลตีความเองจาก "ไพ่ครั้งก่อน → ไพ่ครั้งนี้"

**ขนาดงาน**: ~3-4 ชม. · **ผลกระทบ**: 🔥 สูงมาก · **ความเสี่ยง**: ต่ำ

---

### 3.2 ด่านตรวจความสอดคล้องหลังโมเดลตอบ (Consistency Checker)

**ทำอะไร**: ตรวจผลลัพธ์ JSON แบบ deterministic **ก่อน** ส่งถึงผู้ใช้ ไม่ต้องเรียกโมเดลซ้ำ

ตรวจอะไรบ้าง:

| ตรวจ | ทำไม |
| :--- | :--- |
| `cards[].position` ครบทุกตำแหน่งและไม่ซ้ำ | โมเดลชอบข้ามใบตอนผังใหญ่ |
| **ชื่อไพ่ที่ถูกพูดถึงในเนื้อหา ต้องอยู่ในชุดที่เปิดจริงเท่านั้น** | **ตรงกับกฎเหล็กข้อ 14 โดยตรง** — ตอนนี้กันแค่ระดับข้อมูล ยังไม่ได้กันระดับข้อความ |
| `yesNoAnswer` ต้องไม่ขัดกับ `summary` | ผังใช่/ไม่ใช่ตอบกำกวมบ่อย |
| `advice` ข้อสุดท้ายต้องขึ้นต้นด้วย 🧘 ตามที่สั่ง | ตรวจง่าย เป็นสัญญาณว่าโมเดลทำตามคำสั่งครบไหม |
| ความยาวอยู่ในกรอบ `depth` ที่กำหนด | จับได้ว่าโมเดลเริ่มไม่ทำตามคำสั่ง |

ถ้าไม่ผ่าน → **failover ไปโมเดลถัดไป** (ใช้กลไก `break`/`continue` ที่มีอยู่แล้วใน `groq.ts`) และยิง `recordEvent` ให้เห็นใน `/admin`

**เทคนิคที่ใช้**: *Deterministic Post-Validation* — ตรวจด้วยโค้ด ไม่ใช่ให้ LLM ตรวจ LLM (ถูกกว่า เร็วกว่า เชื่อถือได้กว่า)

**ขนาดงาน**: ~4 ชม. · **ผลกระทบ**: สูง · **ความเสี่ยง**: ต่ำมาก · **ต้นทุนเพิ่ม**: ~0

### 3.3 ตัวอย่างมาตรฐานแบบเลือกตามบริบท (Dynamic Few-Shot)

**ปัญหาปัจจุบัน**: `SYSTEM_CORE_KNOWLEDGE` (7,334 ตัวอักษร) มีตัวอย่างคำอ่านมาตรฐาน **แค่ 1 ตัวอย่าง**
ซึ่งเป็นเคส *ผัง 1 ใบ หมวดการงาน* — แต่ถูกใช้เป็นแม่แบบให้ทุกหมวดและทุกขนาดผัง

ผัง 10 ใบหมวดความรักจึงถูกสอนด้วยตัวอย่างที่หน้าตาไม่เหมือนงานที่ต้องทำเลย

**ทำอะไร**: ทำคลังตัวอย่างที่ผ่านการตรวจแล้ว 6-8 ชิ้น ครอบคลุม (หมวด × ขนาดผัง) แล้ว**เลือกฉีดเฉพาะตัวที่ใกล้เคียงที่สุด 1 ชิ้น**

**ข้อดีแฝง**: system prompt สั้นลงต่อครั้ง (ฉีด 1 ตัวอย่างแทนที่จะแบกทั้งคลัง) = เร็วขึ้นและถูกลง

**ข้อควรระวัง**: ตัวอย่างต้องมาจากคำอ่านที่ผู้ใช้จริงกด `ACCURATE` (ต่อยอดจากเฟส 0)

**ขนาดงาน**: ~1 วัน (ส่วนใหญ่คือเวลาเขียน/คัดตัวอย่างให้ดี) · **ผลกระทบ**: สูง

---

### 3.4 เลือกโมเดลตามความยากของงาน (Model Routing)

ตอนนี้ทุกผังใช้เส้นทางเดียวกันหมด — ไพ่ประจำวัน 1 ใบ กับเซลติกครอส 10 ใบ ใช้โมเดลเดียวกัน ความยาวสูงสุดต่างกันแค่ `max_tokens`

**ทำอะไร**: ผังเล็ก (1-3 ใบ) → โมเดลเร็ว/ถูก · ผังใหญ่ (7-10 ใบ) → โมเดลใหญ่ที่ให้เหตุผลได้ลึก

**ผลตอบแทน**: ผังเล็กคือสัดส่วนการใช้งานส่วนใหญ่ → ตอบไวขึ้นและประหยัดโควตา
เหลือ headroom ไปใช้กับผังใหญ่ที่ต้องการจริง

**ขนาดงาน**: ~3 ชม. · **ผลกระทบ**: กลาง (แต่ช่วยเรื่องต้นทุนและความเร็วชัดเจน)

## 4. 🧪 เฟส 2 — เทคนิคที่ยกเพดานคุณภาพ

### 4.1 RAG จากคลัง Vectorize เข้าคำอ่าน

**ทำอะไร**: ก่อนสร้าง prompt เอา **คำถามของผู้ใช้ + ชื่อไพ่ที่เปิดได้** ไปค้นคลัง Vectorize
ดึงย่อหน้าที่เกี่ยวข้องที่สุด 2-3 ชิ้น (จากคำอธิบายไพ่ 78 ใบ และบทความ 24 ชิ้น) ฉีดเข้า prompt

**เทคนิคที่ใช้**: *Retrieval-Augmented Generation* — ยึดคำอ่านกับเนื้อหาที่เราเขียนเอง แทนความจำของโมเดล

**ทำไมเหมาะกับที่นี่เป็นพิเศษ**:
- เนื้อหาไพ่ 78 ใบเป็นของเราเอง ผ่านการตรวจแล้ว (`verify-cards.ts`)
- บทความ 24 ชิ้นคือน้ำเสียงและมุมมองที่เราอยากให้แม่หมอพูด
- ได้ผลพลอยได้: คำอ่านอ้างอิงบทความของเราเองได้ → **ลิงก์ภายในและเวลาอยู่บนเว็บเพิ่ม**

**ข้อควรระวัง**:
- ⚠️ **เพิ่ม latency** — ต้องเรียก Vectorize ก่อนเริ่มสตรีม ซึ่งกระทบ UX โดยตรง
  ทางแก้: ยิงขนานกับงานเตรียมอย่างอื่น หรือแคชผลตามคู่ (หมวด × ชุดไพ่)
- ต้องกันไม่ให้เนื้อหาที่ดึงมาไปขัดกับไพ่ที่เปิดจริง (RAG ที่ดึงผิดจะทำให้คำอ่านสับสนกว่าเดิม)

**ขนาดงาน**: ~1-2 วัน · **ผลกระทบ**: สูง · **ความเสี่ยง**: กลาง (latency)

---

### 4.2 ขัดเกลาเฉพาะบทสรุป (Targeted Refinement)

**ทำอะไร**: หลังสตรีมคำอ่านรายใบจบแล้ว เรียกโมเดลเร็ว ๆ อีกครั้ง **เฉพาะส่วน `summary` และ `advice`**
โดยให้เห็นคำอ่านทั้งชุดที่เพิ่งเขียนไป แล้วเขียนบทสรุปใหม่ให้คมและตอบคำถามตรงขึ้น

**ทำไมไม่ทำทั้งชุด**: ผู้ใช้เห็นคำอ่านทีละใบแบบสตรีมอยู่แล้ว การขัดทั้งชุดจะทำให้รอสองรอบ
แต่ `summary` เป็นส่วนสุดท้ายที่ผู้ใช้อ่าน และเป็นส่วนที่ตัดสินว่า "แม่นไหม" มากที่สุด

**เทคนิคที่ใช้**: *Two-Pass Refinement แบบจำกัดขอบเขต* — จ่ายเพิ่มเฉพาะจุดที่คุ้ม

**ข้อควรระวัง**: เพิ่มการเรียก AI 1 ครั้งต่อคำอ่าน → **ต้องนับใน `recordAiCall()` ด้วย** (บทเรียนจากแชทถามต่อที่เคยหลุดเพดาน)

**ขนาดงาน**: ~1 วัน · **ผลกระทบ**: กลาง-สูง · **ความเสี่ยง**: สูง (latency + ต้นทุน) → **ต้องมีเฟส 0 ก่อนถึงจะรู้ว่าคุ้มไหม**

---

### 4.3 ให้ 7 โมดูลปรับน้ำหนักตามผลจริง (Adaptive Priors)

**ทำอะไร**: เมื่อมีข้อมูล `outcome` มากพอ (เฟส 0) ดูว่าโมดูลไหนสัมพันธ์กับคำอ่านที่ผู้ใช้บอกว่าแม่น
แล้วให้โมดูลนั้นมีน้ำหนักมากขึ้นใน prompt

ตัวอย่างคำถามที่ตอบได้: *"บทสนทนาทางสายตา (gaze) ช่วยให้แม่นขึ้นจริงไหม หรือแค่ทำให้ prompt ยาวขึ้นเฉย ๆ"*

**นี่คือของที่เว็บดูดวงอื่นทำไม่ได้** เพราะไม่มีทั้งโมดูลวิเคราะห์และวงจรวัดผล

**ขนาดงาน**: ~2-3 วัน · **ต้องมีข้อมูลสะสมก่อนอย่างน้อย 2-3 เดือน**

## 5. 📊 ตารางสรุปลำดับที่แนะนำ

| ลำดับ | งาน | ผลกระทบ | ขนาดงาน | ต้นทุน AI ที่เพิ่ม | ความเสี่ยง |
| :-: | :--- | :-- | :-- | :-- | :-- |
| **0** | เครื่องวัดคุณภาพ + Golden Set | 🔥 บังคับ | ~1 วัน | 0 | ต่ำ |

| **3** | Dynamic Few-Shot | สูง | ~1 วัน | **ลดลง** | ต่ำ |
| **4** | Model Routing ตามขนาดผัง | กลาง | ~3 ชม. | **ลดลง** | ต่ำ |

## 7. 🎯 วัดยังไงว่า "ฉลาดขึ้น" จริง

ห้ามตัดสินด้วยความรู้สึก — ต้องมีตัวเลขทั้ง 3 ชั้น:

| ชั้น | ตัวชี้วัด | อ่านจากไหน |
| :--- | :--- | :--- |
| **ผู้ใช้บอกเอง** | สัดส่วน `ACCURATE` ต่อคำอ่านที่ถูกให้คะแนน · อัตรา `NOT_HAPPENED` ที่ต้องลดลง | `reading_journal.outcome` |
| **พฤติกรรม** | สัดส่วนคนที่กดแชทถามต่อ · จำนวนคำถามต่อรอบ · อัตรากลับมาเปิดไพ่ซ้ำ | `recordEvent` ที่มีอยู่แล้ว |
| **ระบบ** | อัตรา failover · `ai_severe_foreign_leak` · คำอ่านที่ตกด่านความสอดคล้อง · เวลาถึง token แรก | `/admin` |

**กติกา**: แก้ prompt ครั้งไหนต้องขึ้น `prompt_version` แล้วเทียบตัวเลขก่อน/หลังอย่างน้อย 1 สัปดาห์
ถ้าตัวเลขไม่ดีขึ้น = **ย้อนกลับ** ไม่ใช่แก้เพิ่ม

## 8. ❓ สิ่งที่ต้องให้เจ้าของโปรเจกต์ตัดสินใจก่อนเริ่ม

1. **ยอมแลกความเร็วกับความลึกแค่ไหน** — RAG และการขัดเกลาบทสรุปทำให้คำอ่านดีขึ้นแต่ช้าลง
   ตอนนี้ Groq ตอบใน 300-760ms ซึ่งเป็นจุดขาย จะยอมให้ช้าลงกี่วินาที
2. **จะเริ่มเก็บสถิติคุณภาพเลยไหม** — ถ้าเริ่มวันนี้ อีก 2-3 เดือนจะมีข้อมูลพอทำข้อ 7 (Adaptive Priors)
   ถ้าเริ่มทีหลัง ต้องรอใหม่อีกรอบ
3. **ความทรงจำข้ามครั้งจะย้อนหลังกี่ครั้ง** — 1 ครั้งล่าสุด (ปลอดภัย เบา) หรือ 3 ครั้ง (บริบทดีกว่า แต่ prompt ยาวขึ้นและอ่อนไหวเรื่อง PDPA มากขึ้น)
