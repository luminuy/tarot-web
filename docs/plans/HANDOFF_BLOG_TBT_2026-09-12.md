## 📋 ขั้นตอนที่ต้องทำ (ตามลำดับ)

### 1. ยิง Lighthouse ใหม่ แล้วอ่าน "ใครกินเวลา" ไม่ใช่แค่ "กินเท่าไร"

```bash
curl -s "https://www.googleapis.com/pagespeedonline/v5/runPagespeed?url=https%3A%2F%2Fseertarot.net%2Fblog&strategy=mobile&category=performance" -o /tmp/blog_psi.json
```

แล้วอ่าน **3 ด่านนี้** ซึ่งบอกชื่อไฟล์ที่กินเวลาจริง:

| audit | บอกอะไร |
| :--- | :--- |
| `bootup-time` | แต่ละสคริปต์ใช้เวลา parse/compile/execute กี่ ms (**ตัวชี้เป้าที่ดีที่สุด**) |
| `mainthread-work-breakdown` | เวลาแตกตามประเภทงาน (script eval / style / layout / GC) |
| `long-tasks` | งานที่บล็อกเกิน 50 ms พร้อม URL ต้นทาง |

ดึงออกมาด้วย:
```bash
python3 -c "
import json; d=json.load(open('/tmp/blog_psi.json'))
a=d['lighthouseResult']['audits']
for k in ('bootup-time','mainthread-work-breakdown','long-tasks'):
    print('='*70); print(k, '|', a[k].get('displayValue'))
    print(json.dumps(a[k].get('details',{}).get('items',[])[:12], ensure_ascii=False, indent=1))
"
```

## ⚠️ กับดักที่เหยียบมาแล้ว — อย่าเหยียบซ้ำ

### 1. `resource-summary` ของ Lighthouse นับแบบ "คลายบีบแล้ว" ไม่ใช่น้ำหนักที่ผู้ใช้โหลด

รอบ 2026-09-11 อ่าน `resource-summary` ได้ `Script 52 requests / 675 KB` แล้วสรุปว่า `/cards` มีปัญหา JS หนัก
**ผิดทั้งสองตัวเลข**:

| | ที่อ่านมา | ของจริง |
| :--- | :-- | :-- |
| จำนวนสคริปต์ | 52 | **18** |
| ขนาด | 675 KB | 675 KB คือ**ยังไม่บีบ** · วิ่งจริงบนเน็ต **183 KB** (zstd) |

➔ **วัดน้ำหนัก JS ต้องยิงจริงพร้อม `Accept-Encoding: br, gzip, zstd` แล้วอ่าน `size_download`**
ห้ามอ่านจาก `resource-summary` หรือ `encodedBodySize` (ซึ่งคืนค่าเท่า `decodedBodySize` เมื่อโดนแคช)

### 2. Browser pane วัดเวลาไม่ได้ — แกว่งถึง 8 เท่า

โหลด `/blog` สองครั้งติดกันได้ long task รวม **3,844 ms** แล้ว **481 ms**
เพราะ pane ถูกซ่อน (หน้าไม่ถูกวาด) + แชร์ CPU กับงานอื่น
เรื่องเดียวกันเกิดกับการวัด decode ของ AVIF: 3 รอบได้ "ช้ากว่า 3.4 เท่า" → noise → "เร็วกว่า 3.5 เท่า"

➔ **ใช้ Browser pane วัดได้แค่ "จำนวน/ขนาด/ชื่อไฟล์" เท่านั้น ห้ามใช้วัดเวลา** ต้องใช้ Lighthouse

### 3. โควตา PSI แบบไม่ใส่ API key หมดเร็วมาก

รอบ 2026-09-11 ยิงไป ~10 ครั้งก็หมดโควตารายวัน แล้วตรวจอะไรต่อไม่ได้ทั้งวัน

➔ **วางแผนก่อนยิง** ว่าจะเอา URL ไหนบ้าง แล้วยิงรอบเดียวให้ครบ
➔ ถ้าจะทำจริงจังควรขอ API key (`docs/PENDING_SETUP.md`)

### 4. ฟีเจอร์ SEO ที่ Google "ปิดไปแล้ว" — ตรวจปีที่ประกาศก่อนลงแรงเสมอ

รอบ 2026-09-11 เกือบเสนอให้สร้างหน้า `/search` เพื่อใส่ `SearchAction`
จนกระทั่งไปค้นดูจึงพบว่า **Google ปิด sitelinks search box ทิ้งตั้งแต่ 21 พ.ย. 2024**
และประกาศเองว่า `WebSite`/`SearchAction` **ไม่ทำอะไรอีกต่อไป**
➔ ถ้าทำไปคือเสียแรงสร้างหน้าใหม่ทั้งหน้าเพื่อผลลัพธ์ศูนย์

ฟีเจอร์ที่ตายแล้วซึ่งเจอในโปรเจกต์นี้ (อย่าไปไล่ทำอีก):

| markup | สถานะ | ควรทำยังไง |
| :--- | :--- | :--- |
| `SearchAction` (sitelinks search box) | ตาย 21 พ.ย. 2024 | ไม่ต้องเพิ่ม · ที่มีอยู่ไม่ต้องลบ |
| `HowTo` rich result | ตาย ก.ย. 2023 | ไม่ต้องเพิ่ม · ที่มีอยู่ 52 หน้าไม่ต้องลบ (AI ยังอ่านได้) |
| `FAQPage` rich result | ตาย 7 พ.ค. 2026 | ไม่ต้องเพิ่มเพื่อหวังผล SERP · ที่มีอยู่ 121 หน้า **ห้ามลบ** (AI ยังอ้างอิง) |

➔ **ก่อนลงแรงกับ structured data ตัวไหน ให้เช็คก่อนว่า Google ยังรองรับอยู่ไหม**
คู่มือ SEO ส่วนใหญ่บนเน็ตยังเขียนถึงฟีเจอร์เหล่านี้ราวกับยังใช้ได้

> ### ✅ อัปเดต 2026-09-11 — **ทำแล้ว** เพราะเจอเส้นทางที่ไม่มีต้นทุนตามตารางนี้เลย
>
> ข้อสรุป "ยังไม่ทำ" ด้านบนตั้งอยู่บนสมมติฐานว่า **ต้องสร้างไฟล์ `.avif` เก็บในรีโป**
> ซึ่งเป็นที่มาของต้นทุนทั้งหมด (+468 ไฟล์ · +20 MB · gen 21 นาที)
>
> **แต่ ImageKit แปลงให้ตอนร้องขอได้เลย** (`?tr=w-320%2Cf-avif%2Cq-65`) แล้วแคชไว้ที่ CDN ของเขาเอง
> ➔ **0 ไฟล์ใหม่ · 0 MB · ไม่ต้องแตะ `npm run cards:variants` เลยสักบรรทัด**
> ต้นทุนที่เหลือมีอย่างเดียวคือ HTML โตขึ้น +2–3 KB gzip ต่อหน้าที่มีภาพไพ่เยอะ
>
> วัดของจริงที่ w512b เทียบ WebP ที่ใช้อยู่ (PSNR เทียบภาพต้นฉบับย่อ · ไพ่ 4 ใบ):
>
> | รูปแบบ | ขนาดรวม | PSNR | สรุป |
> | :-- | :-- | :-- | :-- |
> | WebP (เดิม) | 408.7 KB | 30.03 dB | — |
> | AVIF q60 | 220.2 KB | 29.76 dB | เบาลง 46% คมน้อยกว่านิดหน่อย |
> | **AVIF q65** | **279.8 KB** | **30.89 dB** | **เบาลง 32% และคมกว่าเดิม** ← เลือกอันนี้ |
>
> ผลรวมทั้งหน้า `/cards` (78 ใบที่ `w320`): **2,725 → 1,893 KB ประหยัด ~832 KB ต่อการเปิดหน้า**
>
> ⚠️ **ข้อกังวลเรื่อง decode บน CPU มือถืออ่อน ๆ ยังไม่ถูกพิสูจน์** (วัดไม่ได้เหมือนเดิม)
> แต่ตอนนี้ถอยกลับได้ทันทีโดยไม่เสียอะไรเลย — ลบ `<source type="image/avif">` บรรทัดเดียว

>
> ⚠️ **ยังลบ WebP ไม่ได้** — Safari ต่ำกว่า 16.4 และเบราว์เซอร์เก่ายังต้องใช้ · `<picture>`
